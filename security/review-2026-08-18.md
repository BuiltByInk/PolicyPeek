## Findings, most severe first

### 1. [HIGH] `ssrf.ts` has no defense against DNS-resolution-based SSRF (wildcard-DNS bypass / rebinding) — the wrapper only inspects the literal hostname/IP string in the URL, never the IP the runtime actually connects to

**File:** `backend/src/ssrf.ts`, `assertSafeUrl()` (lines 102-117) and its use
in `safeFetchText()` (lines 119-171).

**Issue:** `assertSafeUrl` blocks a fixed hostname set and literal IP
addresses/ranges (`isBlockedIpLiteral`), but it never resolves the hostname
and never checks the IP that `fetch()` actually connects to. Any hostname
that is *not itself* a literal IP or in `BLOCKED_HOSTNAMES` sails through the
check, and DNS resolution happens later, inside `fetch()`, completely outside
this wrapper's visibility.

**Concrete failure scenario:** wildcard-DNS services exist specifically to
turn an arbitrary IP into a hostname, e.g. `169-254-169-254.nip.io` resolves
to `169.254.169.254` (the cloud metadata address), and `127-0-0-1.nip.io`
resolves to `127.0.0.1`. An attacker submits:
```
POST /v1/check
{ "domain": "169-254-169-254.nip.io", "source_url": "http://169-254-169-254.nip.io/x" }
```
`isValidDomain` and `isSourceHostAllowedForDomain` both pass (domain and
source host match exactly — this is a legitimate registrable hostname).
`assertSafeUrl` sees the hostname `169-254-169-254.nip.io`, which is not a
literal IP and not in `BLOCKED_HOSTNAMES`, so it passes straight through.
`fetch()` then resolves it via real DNS to `169.254.169.254` and connects —
full SSRF into Cloudflare Workers' internal networking surface (or any other
attacker-chosen IP via any of dozens of similar wildcard-DNS providers, e.g.
`sslip.io`, `xip.io`, or an attacker's own authoritative DNS zone with a
1-second TTL for classic TOCTOU rebinding on the redirect-revalidation path
too — every `assertSafeUrl` re-check on a redirect hop has this exact same
gap).

**Why this matters specifically for this codebase:** this is the literal
attack the docstring at the top of `ssrf.ts` says the wrapper defends
against ("re-validates on every redirect hop rather than trusting fetch's
automatic redirect handling") — but the revalidation only re-checks the
*literal string*, so a rebinding attacker who returns a public IP on the
first lookup and a private IP on the redirect target's lookup is not caught
either.

**Proposed fix (not applied):** Cloudflare Workers' `fetch()` doesn't expose
a resolver hook, but you can regain control by resolving the hostname
yourself (via `DNS-over-HTTPS` to a trusted resolver, e.g. Cloudflare's own
`1.1.1.1/dns-query`, which is reachable from within a Worker) before each
connection attempt, checking every returned A/AAAA record against
`isBlockedIpLiteral`, and rejecting if any resolved address is
private/link-local/loopback/metadata — reject-if-any-bad, not
reject-if-first-bad, since a multi-answer response can rebind on a later
answer. This needs to happen both for the initial URL and after every
redirect hop, since each hop is a fresh DNS resolution. Flag this as a
decision for Backend Agent to implement or explicitly accept as a known
residual risk (log the acceptance in `DECISIONS_NEEDED.md` either way — this
should not be silently left as-is).

### 2. [LOW/PROCESS] The `crossDomainSources.ts` feature and its `check.ts` wiring are not committed — only exist as an untracked file + uncommitted working-tree diff

**Files:** `backend/src/crossDomainSources.ts` (untracked, `git status`
shows `??`), `backend/src/check.ts` (modified, unstaged), plus
`backend/src/check.test.ts`, `DECISIONS_NEEDED.md`,
`frontend/data/tools.json`, `frontend/src/pages/about.astro` (all modified,
unstaged) as of this review.

**Issue:** the mechanism this review was specifically asked to check is not
actually in git history yet. This isn't the D1-migration case the charter
calls out by name, but it's the same underlying risk: a security-relevant
allowlist change that exists only on disk. If this working tree is lost,
reset, or diverges from what another agent/Elliot reviews via `git log`,
the exception silently disappears or silently reappears without a record —
and per this codebase's own stated audit posture (`compliance_changelog`
tracking, "explicit log entry... last build's changelog history got lost
when a trigger silently didn't fire"), untracked security logic is exactly
the kind of gap this project has already been burned by once.

**Proposed fix:** commit `crossDomainSources.ts` and the `check.ts` wiring
(and the other pending changes) with a clear message before treating this
milestone as shipped. Not a code fix — a process one, flagged for Backend
Agent since committing is inside its lane, not mine.

### 3. [LOW] Test suite doesn't prove the cross-domain branch's own boundary logic is narrow, only that a wholly unrelated domain is rejected

**File:** `backend/src/check.test.ts`, lines 34-47.

**Issue:** the existing lookalike-domain regression test
(`"rejects a lookalike domain that merely ends with the same suffix"`,
`evil-acme.com` vs `acme.com`) proves the *primary* exact-match/subdomain
check is boundary-safe. The new cross-domain tests prove the map only fires
for the curated `bolt.new` key, and that a totally unrelated domain
(`evil.com`) still fails. But there's no test analogous to the lookalike
case for the cross-domain target itself — e.g. `evilstackblitz.com` or
`stackblitz.com.evil.com` against `bolt.new`. I traced the implementation by
hand and it's correct today (`isSourceHostAllowedForDomain` reuses the same
`host === cd || host.endsWith('.'+cd)` dot-boundary logic for the
cross-domain branch as the primary one — no bypass currently exists), but
the test suite as written would not catch a future regression where someone
"simplifies" the cross-domain branch to a bare `.includes()` or
`.endsWith(cd)` without the dot.

**Proposed fix:** add
`isSourceHostAllowedForDomain("evilstackblitz.com", "bolt.new")` and
`isSourceHostAllowedForDomain("stackblitz.com.evil.com", "bolt.new")` →
both `false`, mirroring the existing lookalike test for the primary path.

### 4. [INFORMATIONAL] Cross-domain source allowlist itself — checked, clean

`CROSS_DOMAIN_SOURCES` is a hardcoded `Record<string,string>` literal with
one entry, no dynamic population path (no DB read, no env var, no derivation
from fetched page content, no admin-writable table). The lookup in
`isSourceHostAllowedForDomain` is strictly additive to the existing
exact-match/subdomain check and uses the same dot-boundary comparison, so it
can't be tricked into matching a broader pattern than the specific curated
target. `evaluateAutoPublish` (`autoPublish.ts`) doesn't give cross-domain
submissions any different treatment than ordinary submissions — same
treatment as `shared_domain`, which is deliberate per that file's own
comments, not an oversight. No interaction found with `ssrf.ts`,
`sharedDomains.ts`, or `waybackFallback.ts` that reopens the spoofing vector
this exists to close.

### 5. [INFORMATIONAL] Timing-safe admin token comparison — checked, clean

`auth.ts::timingSafeEqual` hashes both the provided token and `env.ADMIN_TOKEN`
with SHA-256 before doing a constant-time XOR-accumulate compare over the
(now fixed-length, 64-hex-char) digests. This avoids both the naive `===`
length/short-circuit leak and a same-length-but-early-exit leak. `requireAdminToken`'s
early `!provided || !env.ADMIN_TOKEN` return is a presence check, not a
value comparison, so it doesn't reintroduce a timing side-channel on the
actual secret.

### 6. [INFORMATIONAL] XSS — checked, clean; no `set:html` anywhere in the frontend

Grepped the full `frontend/src` tree: no `set:html`, no `innerHTML`, no
`dangerouslySetInnerHTML` usage anywhere. Every LLM-extracted or
tool-submitted string that reaches a template (`tool.name`, `tool.summary`,
`facts.relevant_clauses[0]` surfaced via `summary`, `tool.domain`,
`tool.source_urls`) is rendered via Astro's default `{expression}`
interpolation, which HTML-escapes in both text and attribute position. The
`SubmitTool.astro` client-side script uses `status.textContent =`
exclusively, never innerHTML, so a domain/URL containing HTML in the status
message can't execute either. `tool.source_urls` rendered as `href={url}`
is not exposed to a `javascript:`/`data:` URI injection in practice, because
any such URL would parse to an empty `URL.hostname` and fail
`isSourceHostAllowedForDomain`'s domain-match check in `check.ts` before it
is ever stored — so a script-scheme source URL can never reach the DB in the
first place. (This matches the `<script>`-payload fixture mentioned as
tested today — it reflects real, structural escaping via Astro's default
behavior, not a one-off check.)

### 7. [INFORMATIONAL] CORS configuration — checked, appropriately scoped

`cors.ts` applies a wildcard `Access-Control-Allow-Origin: *` only to
`/v1/lookup` and `/v1/check`, both of which are unauthenticated-by-design,
non-cookie, rate-limited public endpoints (per `CLAUDE.md`'s ICP decision:
checking must not be gated). Admin routes (`/v1/admin/...`) never go through
`withCors`/`corsPreflightResponse` — `index.ts` only applies CORS to the two
public paths, and an `OPTIONS` request to an admin path isn't special-cased,
so it falls through to the normal `requireAdminToken` gate (fails, 401) with
no CORS headers attached either way. No credentialed (cookie) auth exists
anywhere in this backend, so a wildcard origin here doesn't expose anything
a direct `curl`/`fetch` from a script couldn't already reach.

### 8. [INFORMATIONAL] Anonymous `/v1/check` rate cap and admin auth path — no regression found

- `isUnderDailyCap`/`recordAnonymousCheck` (`rateLimit.ts`) are called in the
  right order in `handleCheck` (cap-check before the costly fetch+LLM work,
  record only after the `pending_checks` insert actually succeeds) — a
  rejected/invalid submission doesn't burn the caller's daily slot, matching
  the file's own stated intent.
- `getClientIp` trusts `CF-Connecting-IP` first (edge-set, not
  client-spoofable through Cloudflare's network) and only falls back to the
  client-suppliable `X-Forwarded-For` when that header is absent (i.e., only
  relevant for local `wrangler dev`, not real traffic through Cloudflare's
  edge) — this is a reasonable, already-documented tradeoff, not a new
  regression.
- Every endpoint that should require the admin token does:
  `/v1/admin/pending`, `/v1/admin/pending/:id/approve`, and
  `/v1/admin/pending/:id/reject` are all behind a single `requireAdminToken`
  gate in `index.ts` before the path/method is even switched on, so there's
  no route inside that regex match that can be reached without the token.
  `/v1/lookup` and `/v1/check` are intentionally public per the ICP decision
  in `CLAUDE.md` and are not missing auth — they're gated by the daily cap
  instead, which is the documented design, not an oversight.
- All 51 backend tests pass (`npx vitest run`), including the CORS,
  rate-limit, and auth suites — nothing here is failing silently.
