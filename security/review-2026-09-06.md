### 1. [INFORMATIONAL] `check.ts`'s new try/catch — reviewed, no new exposure

The only code change: the auto-publish step (`evaluateAutoPublish` +
`approvePendingCheck`) is now wrapped in its own `try/catch`, writing
`` `auto_publish_failed: ${err.message}` `` to `pending_checks.extraction_error`
on failure instead of failing as a silent unhandled `ctx.waitUntil`
rejection (see `DECISIONS_NEEDED.md`, 2026-09-01). Checked for security
implications specifically:

- The error message is bound via `.bind()` (parameterized), never
  string-concatenated into SQL — no injection surface regardless of what a
  D1 error message contains.
- `extraction_error` is only ever read back through `GET /v1/admin/pending`,
  which is behind `requireAdminToken` — the same gate finding #8 of the last
  review confirmed covers every admin route. No new public exposure.
- The messages actually seen in practice (`D1_ERROR: CHECK constraint
  failed...`) are DB schema errors, not credentials or PII.

No finding here — purely defensive, correctly scoped.

## Batch traffic pattern — what was and wasn't actually stress-tested

Phase 2's kickoff specifically asked to check SSRF/rate-limiting "under the
actual batch traffic pattern," so this is worth being precise about rather
than assuming a clean bill of health:

### 2. [INFORMATIONAL] The 19-tool batch was sequential, not concurrent — a real gap in what's been proven, not a vulnerability

The batch runner script used for Phase 2 (a scratch script outside this repo,
not committed) submitted one `POST /v1/check` at a time and polled for that
submission's extraction to finish before submitting the next. That means Phase 2 proved **correctness** at
volume (19 real extractions, real verdicts, real auto-publish decisions) but
did **not** exercise `safeFetchText`'s DNS-resolution SSRF check or
`isUnderDailyCap`'s rate-limit read/write under genuine concurrent load
(e.g., several `fetch()`+DoH-resolution calls racing, or several
`anonymous_check_log` inserts racing on the same IP bucket at once). D1's
own transaction semantics make a rate-limit race unlikely to actually be
exploitable, but "unlikely by db semantics" isn't the same as "tested" —
flagging the gap honestly rather than claiming concurrency was validated
when it wasn't. Not blocking Phase 3, but worth a real concurrent-load test
before this handles genuine public traffic, not scripted sequential batches.

### 3. [INFORMATIONAL] Free-tier daily cap was correctly bypassed for testing, not weakened

Phase 2 used a temporary, local-only `paid`-tier API key (`api_keys.id = 1`,
label `phase2-bulk-run-internal`) specifically so batch submissions didn't
trip the real 1-per-24h anonymous cap — this is `resolveTier`/`isUnderDailyCap`
working exactly as designed (a registered paid key is exempt by design, see
`CLAUDE.md`), not a bypass of a control. Confirmed the key was revoked
(`revoked = 1`) immediately after Phase 2's bulk run completed (verified
2026-09-02, logged in `changelog.md`). Confirmed today: **remote D1's
`api_keys` table has zero rows** — this local-only test credential was never
inserted into, or anywhere near, the real database. No exposure.
