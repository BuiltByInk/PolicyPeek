# Team meeting, 2026-09-19

Run by the main Claude session acting as manager (see the note in `decision_log.md`). Six agents were asked the same six questions read-only: recent work, blockers, needs, conflicts and gaps, the one change that would help most, what to stop. Their answers are model output; where I checked something myself it says "checked". Two follow-up jobs came out of the meeting and are covered at the end: a fact-check of the auto-published favourable badges and an independent security review.

## What each agent said

**Backend.** Tests use a hand-rolled fake database, so nothing proves the schema, triggers or migrations against real SQLite. Wants a test harness that applies `schema.sql` and the migrations to in-memory SQLite (needs Write and probably a dev dependency). Can't see whether the `not_ai_tool` migration ran in production. Notes the `rules.ts` boundary is ambiguous ("interim" fixes keep landing there), and that nobody owns dashboard-only settings. Wants the item 8 ruling.

**Frontend.** Its written definition (Read, Edit) conflicts with what it needs (create files such as `privacy.astro`, run builds). No tests for the frontend or extension; earlier browser checks weren't saved. Nobody owns the extension (manifest permissions, store submission, API shape). The site is static, so a published tool only appears after a manual refresh. Asks for Write and Bash scoped to `frontend/` and `extension/`, ownership of the extension, and a stable documented shape for the API responses. Says: stop UI polish until the extension is in a store and there are users.

**Security.** The 2026-09-19 fixes were written and reviewed in one session; wants an independent pass (commissioned, below). Can't see production config, can't run `npm audit` or tests under its definition, no CI. Flags: `backend/.dev.vars` holds a key-shaped value (checked: untracked, gitignored, never in git history); tracked SQL dumps contain client IPs (checked, true); `sharedDomains.ts` doesn't list hosting domains like github.io, vercel.app, pages.dev, notion.site (unchecked). Wants a pre-deploy gate (built, below) and says the "favourable badge for a brand-new domain" risk should be guarded now, not after traffic.

**Research.** 59 tools sourced, 33 published, and nothing shows what the last 5 submissions became. Sites that block fetching are dropped or marked low-confidence. `tool_sources.json` has no structured place for plan tiers, verification method or check date. Nobody re-checks published verdicts against source text over time. Wants a read-only outcomes view (helper built, below). Says: stop adding sourcing batches until outcomes are visible, and sample-audit auto-published badges before anything public.

**Docs.** `DECISIONS_NEEDED.md` is 2,586 lines / 60 headings with 28 marked Resolved (checked); many "Open" entries are stale. README and PROGRESS haven't changed since 6 Aug, and ARCHITECTURE_NOTES predates the last month of work. Docs is only allowed three files while the charter says it syncs README and architecture docs. Nobody keeps the deploy runbook or the published privacy text current. Wants its scope widened and permission to split `DECISIONS_NEEDED.md` into a short "Open" file plus an archive.

**Marketing.** Wants Search Console exports (in `research/marketing/gsc/`), a ruling on two suspect verdicts, a one-line "what is live" note after each deploy, a copy of built HTML to check head tags, the research agent's batch status, and a contact route and legal name for the privacy page. Also asked whether it may hand the manager text for `DECISIONS_NEEDED.md`, which it can't edit.

## What several agents said (the real themes)

1. **Trust in auto-published badges is the biggest risk.** Research, security, marketing and (in the audit) the evidence all point the same way. See the fact-check: of 13 favourable auto-published badges, 2 are clearly supported, 2 unsupported, 6 unclear, 3 unverifiable.
2. **Agent definitions don't match how work is really done.** Backend, frontend, security and docs each have tool limits narrower than the jobs they're given, and the extension and the deploy runbook have no owner.
3. **Docs sprawl.** Long append-only files hide what is open. Rulings should move into a short current-state doc and the narrative should be archived.
4. **Dashboard-only settings are invisible.** Rate limits, the Anthropic spend limit and `ADMIN_TOKEN` strength aren't in the repo or checkable from here.
5. **The deploy is the bottleneck.** A stack of changes is waiting on tonight's manual steps; the more that piles up, the riskier it gets. The runbook already stages it (migration, backend, re-approve, site, extension).

## Decided by the manager (all in `decision_log.md`)

Pause new sourcing batches (M1); commission the fact-check (M2) and independent security review (M3); write down ownership for the extension, SEO, runbook and `DECISIONS_NEEDED.md` (M4); built `scripts/predeploy-check.mjs` and `scripts/batch-outcomes.mjs` (M5); checked two claims (M6); logged the marketing agent's live-site findings and the fact-check result (M7, M8).
